Diagnosing 5G drive-test degradation
with LM function calling

Eight root causes, one label per case. The model may not read a verdict from anywhere: every number it uses must come from a deterministic, label-neutral measurement tool that it chooses and calls itself. This report covers what was built, what each component is worth in measured points, and — separately and in full — what failed.

The task

Each case is a drive-test table plus engineering parameters, and a question: why does throughput fall below the stated criterion on some road sections? Exactly one of eight causes is correct.

Four causes are decided by an exact criterion — serving distance > 1 km, ≥ 3 PCI changes, speed > 40 km/h, mean scheduled RBs < 160. The other four (weak far-end coverage, better neighbour throughput, overlapping co-frequency neighbours, PCI mod-30 collision) have no exact criterion and must be tie-broken from measurements.

The constraint we imposed

Six tools return measurements only. An automated check (assert_label_neutral) fails any tool output that contains a class token or a field named like a verdict, so no tool can leak an answer — not even accidentally.

Consequence: the model owns tool choice, tool order, and the decision. Nothing in the pipeline may hand it a label, including the consistency verifier, which only ever points at the model's own text.

What actually moved the number

Not prompt wording. Instruction seeds and bootstrapped demos plateaued early and stayed flat. Every subsequent gain came from mechanism: an audit-and-retry loop, a decorrelated third voter with a precision-weighted aggregator, and — largest of all — giving the hard decision its own undistracted call.

The last of those made the ensemble unnecessary: one program with a residual specialist beats three programs voting, by 3.24 points, at 45% of the cost. Two other mechanisms that looked promising delivered nothing; both are reported below with the measurements that killed them.

Architecture

Everything here is one tool-calling procedure used more than once. Figure 1 is that procedure — the only place raw data is ever touched. Figures 2 and 3 are the two configurations built around it: run it three times and vote, or run it once and add a focused second decision. Figure 3 is what ships; Figure 2 is kept because it was the shipped system for three rounds and its measurements are what motivated Figure 3. Figure 4 is the road not taken — the same defect attacked by training the weights instead of changing the architecture — and it is drawn here because measuring it is what proved the architectural fix was the right one. Nothing is modelled on an external architecture; the only off-the-shelf part is the ReAct loop itself, taken from dspy.ReAct.

What RL did not learn — and it is measurable

Gate-verdict discipline. C8 is 2/12 native (base 0/12), failing as 100.98 > 160 → not triggered — a false inequality — and 105.57 < 160 → not triggered — a correct inequality with the wrong verdict. Those are text-internal contradictions, which is exactly what the verifier catches, and why the shipped pipeline holds C8 at 108/108.

Tool initiative, where the demonstrations leave it to the model. Under seed v11 plain-ReAct stage-2 coverage halves, 19–21% → 9.4%. Under seed 4, whose demonstrations call all six tools every time, it is unchanged (51.0% → 54.2%). The shipped pipeline barely notices either way — forced-measurement rounds go 41/96 to 43/96 — because it never relied on that initiative in the first place.

The one-sentence comparison

Figure 3 and Figure 4 attack the identical defect — a decision made in a prompt that is simultaneously carrying four gate criteria, eight cause definitions and a drive-test table. Figure 3 deletes the crowding and costs one extra LM call per residual case. Figure 4 trains through the crowding and costs 21 GPU-hours. Both work; measured together they are worth p = 1.0. The architectural fix arrived first and is free, so it ships — and the RL run keeps its value as the independent second measurement that the diagnosis was right.

Why Figure 3 exists — the measurement that motivated it

Take the 376 official residual cases, guarantee all six observations are present, and leave the rule order printed verbatim in the prompt. The model scores 47.9%. A plain-Python executor of the same rules on the same numbers scores 76.9%. That is 109 cases lost with nothing missing — no absent measurement, no unstated rule. The prompt was simultaneously carrying four gate criteria, eight cause definitions and the full drive-test table. The hypothesis: the model can do the arithmetic, but not while also holding everything else.

What Figure 3 delivered — confirmed on official-864

On the 432 cases whose true label is a residual class, accuracy went from 53.7% (audit-and-retry) to 72.5%, against a symbolic ceiling of 79.9% on the same cases. Moving one decision into its own call recovered 72% of the entire LM-versus-Python gap, and the gate half stayed at 432/432.

The tool layer — what the model may look at

Nothing in the pipeline reads the raw tables except the tools. The model is handed the case text and a catalog of six functions; it decides which to call, in what order, and when it has enough. Each function returns measurements only — an automated check rejects any output that contains a class token or a verdict-like field name, so a tool cannot leak the answer even by accident.

How often each function is actually called · official-864

Stage 1 is near-universal, but the two stage-2 functions — the only evidence for C4 and C6 — are called on roughly a quarter of cases by ballot A and a fifth by the thinking ballot, against a residual zone of 43.5%. Ballot B calls them on 50.9% because its bootstrapped demonstrations always do; the behaviour is inherited from examples, not from the instruction, which is identical. The shipped configuration reaches 52.4% by executing the skipped call itself — 99.5% of the cases that actually need it, and never on a gate case.

Tool calls per case · ballot A

Four calls is the gate path and it accounts for 480 of 864 cases. Seven and eight calls are audit retries re-measuring, not richer exploration: the retry re-runs the whole trajectory, which is why a flagged case costs 3.7× a clean one.

Why tool discipline is the recurring theme of this project

Three of the four mechanisms in this report exist because the model skips measurements it was told to take. The verifier detects the skip and asks; the forced-measurement variant executes the missing call itself; the specialist decides only after the numbers exist. Measured on official-864, a residual answer backed by both stage-2 observations is 63.9% correct, and one without them is 34.1% — the same model, the same prompt, the same case.

Where DSPy is used — and where it is not

DSPy supplies the program abstraction and the prompt optimizers. It does not supply the tools, the audit, the aggregator, or the evaluation protocol — those are ours, and they are where the measured gains came from. The boundary matters for reproducing this work, so it is drawn explicitly.

Is the answer computed by code?

This is the first question any reviewer should ask of a system that pairs a language model with deterministic tools, and the design has to survive it on evidence rather than assurance. Four checks below; each one is verifiable in the repository, and the fourth is the one that actually settles it.

check 1No tool can return a class — enforced, not promised

assert_label_neutral runs on every observation before the model sees it, including the ones forced measurement executes on the model's behalf. It raises AssertionError on any C1–C8 token anywhere in the serialized output, and on any field named answer, label, gate, triggered, diagnosis or root_cause.

It is an assertion, not a warning: a leak crashes the run rather than degrading it quietly. Every number the model quotes has to have come through this gate.

check 2No audit message names a class

The consistency verifier has 17 places where it can raise a flag. Zero of them contain a class token. Every message either quotes the model's own sentence back at it — "a comparison that makes a criterion true, then labelled not triggered" — or names a tool it never called.

The verifier knows a trace contradicts itself. It does not know, and is never told, which of the eight causes is correct.

check 3The Python solver exists — and is never on the answer path

We did write a plain-Python executor of the published decision flow. It scores 89.93%. It is used for exactly two things: as the ceiling that the LM pipeline is measured against, and as an offline audit of where the policy itself is wrong.

No code path in the shipped program imports or calls it. Reporting it openly is the point — a hidden solver would be the thing to worry about.

check 4The measurement that settles it

If code were deciding, the two numbers would be identical. They are not:

The division of labour, stated plainly

Deterministic code doesThe model does
Parse the drive-test tables. Compute the measurements. Refuse to emit anything that looks like a verdict. Detect self-contradiction in a finished trace. Execute a measurement the model skipped. Choose which of the six tools to call, in what order, and when it has enough. Write the verification line for every criterion. Decide the class. Decide whether the case is residual at all — which is what routes it to the specialist.

The executor is handed every feature by construction. The model has to go and get them, and on 43.5% of cases it needs a second round of measurement before it can decide. That is the part no rule engine performs.

What is fitted from data, and disclosed

Two quantities in the residual tie-break are calibrated rather than given: the rule order (C6 before C4 before C1) and the 142.5 Mbps threshold. Both were fitted on the training split only — 567 residual training cases — and neither has been retuned since. They are written into the prompt as domain knowledge, the way an engineer would be handed a troubleshooting procedure, and they are never applied by code at inference time. The four exact criteria (1 km, 3 PCI changes, 40 km/h, 160 RB) are given by the task definition and were not fitted at all.

Why the two layers are separate

The audited lines cannot be softened: the consistency verifier parses exactly that format — field name, signed inequality, verdict word — so relaxing it would blind the audit. Instead of asking one string to be both machine-checkable and readable, the pipeline keeps both: the verdict rests only on the audited lines, and the narrative is a presentation layer that can be regenerated, translated (--narrate-language), or dropped without touching a single decision. Validated on the shipped configuration: 96/96 cases produced a narrative, 1/96 tripped the grounding guard — and that one is shown above, annotated, not hidden.

Quality per unit cost — the unusual part of this result

The shipped configuration is simultaneously the most accurate and the cheapest useful one: 86.23% against the ensemble's 82.99% at 45% of its LM calls and 31% of its serial wall-clock. Accuracy and cost usually trade against each other here; they did not, because the ensemble was paying three times over to work around a defect — one crowded decision — that the specialist removes outright.

Where the wall-clock goes

The thinking ballot alone is about two thirds of the ensemble's serial time and carries the widest variance (±4.6 points draw to draw). Removing it was the single biggest cost lever, and the specialist pipeline does exactly that. The full 864-case test now runs in 26.5 min at 12 workers instead of 89.3 min.

Method and statistical discipline

Splits

  • dev-96 — 12 per class, hash-split from the training pool. Used for selection.
  • sel200 — 200 further training-pool cases, past the window the demo bootstrapper drew from. Added in round 4 after dev-96 selected noise three times.
  • holdout-96 — untouched confirmation set.
  • official-864 — the frozen test file. Every run against it is pre-registered with its configuration before it starts.

Why selection moved off dev-96

At p ≈ 0.8 a 96-case set has 1σ ≈ ±4.4 points. Three times a change that looked decisive on dev-96 did not survive: the audit-weighted aggregator, the size of the forced-measurement gain, and the forced-measurement gain itself.

Selection now uses dev-96 + sel200 = 296 cases and every comparison is a paired McNemar test, not a difference of two accuracies.

Label neutrality, enforced rather than promised

Every tool output passes assert_label_neutral, which rejects any class token and any field named answer, label, gate, triggered, diagnosis or root_cause. The consistency verifier never names a class: each retry message quotes the model's own sentence or names a tool it skipped. The RL reward function is the only place a gold label appears, and it is never visible in a prompt. The symbolic reference is used as an audit and a ceiling, never as an answer path.

What is still open

untriedVote over specialists

The two mechanisms are orthogonal and were never combined: every ensemble measurement predates the specialist. 62 of the 119 remaining errors have the gold label on some run already on file, and an oracle over everything scores 98.50%.

regressionThe C1 the specialist gave away

Against the ensemble it gains +42 C3 and +26 C4 but loses 20 net on C1 (63.9% vs 82.4%). Rule 1 claims those cases for C3 before the C1 rule is reached, so a C1-versus-C3 discriminator is worth about 2 points on its own.

feature gapSeparating C4

56/108 on official — the weak class in every configuration ever run, and 52 of the 119 remaining errors. The 33-case overlap zone shows this needs a new discriminating measurement, not a better prompt.

openRL aimed somewhere else

GRPO v1 finished and proved redundant with the specialist. What it demonstrably did not learn is gate-verdict discipline — the C8 pathology the verifier catches. A run targeting that, or the 44 execution errors, is the version worth training.
