Câu nào hay sai? (96 câu × 8 run — càng tối càng khó)

Mỗi ô là một câu dev, độ sáng = số run trả lời đúng (0–8). Bốn hàng gate sáng đều; cái khó dồn hết vào C1/C3/C4/C6. Viền đỏ = "lõi cứng" sai ≥7/8 run (2 câu, đều gold C4). Hover xem câu sai thành gì.

Sai theo kiểu nào? (lỗi trung bình mỗi run, theo họ cấu hình)

Câu chuyện dịch chuyển: base sai chủ yếu vì KHÔNG ĐO (bỏ giai đoạn 2 rồi vẫn kết luận); verifier ép đo nên lỗi còn lại dồn về "đo đủ nhưng chọn sai luật"; thinking tự suy diễn thay vì đo — vừa bỏ đo nhiều nhất vừa là họ duy nhất vượt cả gate.

Tool gọi sai như nào — và đúng ra phải như nào

Quy trình chuẩn: case có gate → gọi đúng 4 tool rồi DỪNG · case residual → đủ 6 tool (thêm pci_relations + neighbor_overlap) trước khi kết luận.
Verifier là thứ duy nhất kéo được kỷ luật đo residual (28% → 78%); thinking gần như bỏ quy trình (32%). Gọi trùng tool không gây sai đáp án nhưng tốn ~lượt gọi (base tệ nhất: 38% số run).

Vậy trục prompt đã cạn chưa?

Phân rã 190 lỗi ở trên cho câu trả lời có bằng chứng, chia 3 nhóm:
  • Phần chữ nghĩa: cạn thật. 7 đời seed (v5→v11) đã bão hòa gates 48/48 và đứng ở 72.92% — seed11 không hơn seed9; xổ số demo đã thử cạn. Lỗi còn lại không phải do model "không hiểu chỉ dẫn".
  • Lỗi thực thi & kỷ luật quy trình: còn cải thiện được, nhưng bằng MECHANISM chứ không phải câu chữ. Bằng chứng: verifier (một cơ chế, zero prompt mới) kéo kỷ luật đo 28%→78% và +3.1 điểm; phát hiện hôm nay (C4→C3 lật cực, 50 lỗi) nằm đúng điểm mù v1 → verifier v2 là nước đi cụ thể tiếp theo.
  • Giới hạn policy: prompt vô can. Chạy quy trình HOÀN HẢO bằng Python cũng chỉ 96.88% dev (74.96% trên residual train) và sai đúng các cặp C3↔C4/C6 mà model sai — muốn qua phải có feature phân tách tốt hơn hoặc policy học được (GRPO đang train).
DSPy còn đúng một nước chưa thử: GEPA/MIPRO với reflector mạnh (Qwen3.5-122B qua gateway, cần key) — kỳ vọng một-vài điểm, thấp hơn nhiều so với verifier v2 + ensemble + RL đang chạy.

Ensemble hoạt động thế nào

Mỗi case lấy đa số phiếu; hòa phiếu thì ưu tiên verifier-s11 (tất định, gates chắc nhất). Tổ hợp 3 phiếu = verifier-s11 + verifier-s4 + 1 run thinking tươi:
  • Hai phiếu verifier tất định làm mỏ neo (gates 48/48, bù trừ nhau: v-s11 mạnh C1/C8, v-s4 mạnh C4/C6) — phiếu thinking bơm C3.
  • Kết quả qua 5 lần gieo phiếu thinking: 83.3 / 80.2 / 81.25 / 79.2 / 79.2 → kỳ vọng 80.62% ± 1.7 (so với single thinking ±4.6).
  • Chi phí ≈ 2.6× base về compute; wall-clock ≈ một run thinking nếu chạy 3 phiếu song song.
  • 7 phiếu (5 thinking + 2 verifier) = 81.25% — thêm 4 run thinking chỉ mua thêm ~0.6 điểm.
